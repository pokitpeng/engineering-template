# 可观测性基线

本文件是所有新项目默认继承的工程要求，不表示模板已包含埋点 SDK、采集服务或经过验证的运行时实现。项目选择技术栈后，由 AI 实现并提交验收证据；不适用项必须写明理由、替代验证方式和负责人批准记录。

项目具体配置以 [可观测性设计](../architecture/observability.md) 为准，验证场景见 [验收清单](../acceptance/observability.md)。基础设施细节不应在每份功能规格中重复。

## 目标与边界

应能回答：哪个版本在什么环境发生了什么、影响多大、请求经过哪些组件、在哪里慢或失败、如何验证修复。

日志解释离散事件，指标度量趋势与影响，链路追踪定位跨边界耗时与因果。三者互补，不能替代测试、代码审查、安全审计或业务正确性证明。“详细”指有诊断价值的上下文，不是默认输出所有变量、输入和响应。

默认优先使用 OpenTelemetry 兼容的埋点和 W3C Trace Context；不指定日志库、语言、数据库、采集后端或云厂商。不同选型需在架构设计中说明映射和兼容方式。

## OBS-001：统一身份与配置

- 三类信号具有一致的服务名、版本、部署环境；能区分实例，实例标识不默认成为所有业务指标的标签。
- 统一封装初始化、上下文、脱敏、导出和关闭逻辑，业务模块不得自行建立互不兼容的采集链路。
- 日志级别、导出端点、采样、超时、缓冲容量及开关通过受控配置管理，不硬编码秘密。
- 对无效配置定义显式处理策略；遥测后端故障不应被误判为业务服务不可用。

## OBS-002：结构化日志

生产日志使用 JSON 或可映射到等价结构的日志协议。项目在架构设计中声明字段映射：

| 逻辑字段 | 要求 |
| --- | --- |
| `timestamp` | UTC 时间，统一格式与精度 |
| `severity` | DEBUG / INFO / WARN / ERROR，含义一致 |
| `service.name`、`service.version`、`deployment.environment.name` | 信号共有身份 |
| `event.name` | 稳定事件名称，禁止把动态数据拼成事件名 |
| `message` | 简短描述，不作为唯一查询或聚合依据 |
| `operation`、`outcome` | 适用时记录操作和有界结果分类 |
| `trace_id`、`span_id` | 有有效追踪上下文时记录；没有时不伪造 |
| `request_id` / `job_id` | 适用时提供关联标识，限制长度并验证来源 |
| `error.type` / `error.code` | 失败时使用稳定分类；堆栈必须脱敏 |
| `duration_ms` | 记录耗时时使用非负数值及明确单位 |

必须覆盖启动/关闭、关键业务状态变化、操作最终结果和依赖失败；预期业务拒绝应与系统故障区分。指定失败记录的责任边界，避免每层重复输出同一个错误堆栈。

生产默认 INFO；DEBUG 临时启用需有范围、权限、到期恢复及容量限制。对重复日志限速时，应保留汇总与丢弃计数，不能无声丢弃。日志失败不得引发递归记录。

## OBS-003：可聚合指标

- 在线服务覆盖请求/任务吞吐、成功/失败、延迟分布及资源/队列饱和度；按实际架构补充依赖、连接池、积压和重试等指标。
- 关键业务结果应有有界分类的指标，区分技术成功与业务成功。
- 每个指标说明名称、类型、单位、计数时机、分母、标签及其允许值；延迟使用能聚合的直方图并按目标配置桶，不能只报告平均值。
- 区分逻辑操作与重试尝试，避免重试造成成功率分母重复；排除或独立统计探针流量。
- 用户 ID、订单 ID、请求 ID、trace ID、原始 URL、自由文本、错误堆栈禁止作为常规指标标签。HTTP 路径使用路由模板或有界兜底值。
- 指标不能依赖 trace 被采样或日志被保留；必须为标签组合和活跃时间序列制定预算。需要关联 trace 时使用后端支持的 exemplar，而不是 trace ID 标签。

## OBS-004：端到端链路与上下文

- 覆盖实际存在的 HTTP/RPC 入口与出口、数据库、缓存、消息生产/消费、后台任务等边界。不是给每个函数创建 span。
- 支持 W3C `traceparent` / `tracestate` 的受控传播；验证不可信入站上下文，拒绝无效格式。外部输入不具有身份认证或授权含义，也不得强制突破本地采样预算。
- Span 名称稳定且低基数，记录操作、耗时、结果和安全的依赖属性；系统失败按所选语义约定标记 error，取消、业务拒绝等单独分类。
- 重试需可辨认每次尝试与最终逻辑结果；并发、跨线程/协程和异步队列显式传播上下文。批处理或延迟任务按语义选择 parent 或 span link，不能串错请求。
- 日志关联到当前 trace/span。采样未保留的 trace 可能无法查询，不得伪造“可跳转”证据。
- 不默认传播任意 baggage；外发域名、字段与长度采用白名单。

## OBS-005：数据最小化与访问安全

- 日志、span、指标、采集器配置及验收样本均不得包含密码、令牌、Cookie、连接凭证或不必要的个人敏感信息。
- 默认不采集完整请求/响应正文、HTTP 头、SQL 参数、消息载荷、浏览器输入或页面 DOM；必须使用字段白名单并在发送前脱敏、截断和转义。
- 异常消息、堆栈、URL 查询参数同样可能泄密，不能只脱敏结构字段。用户输入不得改变日志结构。
- 标识符哈希不自动等于匿名化，允许记录的业务 ID 需评估敏感性和访问范围。
- 为存储、传输、访问控制、保留与删除制定策略；指标/采集端点不得无保护暴露到公网。
- 安全/合规审计日志若要求不可丢失，必须采用独立保障策略；不能用可采样的诊断日志冒充审计证据。

## OBS-006：采样、容量与性能预算

- 按环境定义 trace 采样、日志速率/大小、指标序列、保留期及 CPU/内存/延迟开销预算，给出实测结果。
- 全量采集仅可在受控测试或有明确容量预算的场景使用，生产不得无评估全量输出 DEBUG 或载荷。
- 头部采样可能丢弃之后才发生的错误；若要求优先保留错误或慢链路，设计尾部采样或替代诊断机制，说明资源成本及仍可能丢失的情况。不声称所有错误 trace 都能保留。
- 采样率降低不得影响核心业务计数与错误率计算。后端/导出异常时能识别数据缺失，而不是将“没有数据”当成“没有故障”。

## OBS-007：遥测故障隔离

- 普通诊断信号导出必须使用有界队列、有限超时和有上限的重试/退避；队列满时按明确策略降级，并计数丢弃量。
- 采集器不可达、慢响应、磁盘满（如适用）不得导致无限阻塞、无限内存增长或业务进程崩溃。
- 关闭时有限时 flush，超时后退出，不保证进程崩溃时全部数据送达。
- 监控导出失败、队列占用、丢弃量和采集器健康；全链路采集故障需有独立存活检查或其他带外信号，不能只依赖已经故障的导出通道。
- 合规审计的故障行为另行评估和批准，不能直接套用诊断信号的丢弃策略。

## OBS-008：可操作的监控与排障

- 关键用户路径定义 SLI/SLO，包括窗口、成功定义、阈值与无流量处理。阈值需结合产品目标，不随意填数。
- 提供可执行查询、仪表盘及告警配置：流量、错误、延迟、资源/队列、依赖和遥测自身健康。
- 告警包含负责人、严重级别、持续时间、去抖/恢复条件、无数据行为和关联 runbook；优先告警用户影响，避免为每条错误日志单独告警。
- Runbook 给出从指标到 trace、再到关联日志的步骤及采样缺失时的替代路径，包含验证、恢复和升级处理。查询必须在实际后端验证，不能仅提交空链接。

## OBS-009：按运行形态覆盖

- 后端服务、Worker、CLI/批处理和前端都需评估三个信号，不能把“非 HTTP 服务”当作不需要观测。
- 浏览器/客户端覆盖关键交互性能、网络失败、未捕获异常和版本关联；离线、未同意采集或发送失败不得阻止核心功能。用户可见内容不携带秘密或堆栈。
- 浏览器不保存后端导出密钥，不默认向第三方请求传播上下文；使用受保护、限流的采集入口及必要的同意/隐私策略。
- 单体、离线工具或受限设备可使用本地输出等适配方式；不强迫部署完整分布式基础设施。裁剪理由、替代证据和审批需记录。

## OBS-010：验证与交付证据

功能实现必须同时交付适用的日志、指标、trace、测试、排障说明与配置。测试至少覆盖正常、业务拒绝、系统失败/超时、重试/异步关联、敏感数据、基数控制和导出故障。

验收使用合成数据并记录版本、环境、步骤、断言与脱敏证据；必须证明信号经过真实项目导出链路后可查询，不只是 SDK 调用成功。无法完成的测试明确标记阻塞项，不自动宣称功能已交付。

通用模板 CI 只验证文档结构和链接，不验证任何运行时可观测性要求。项目需把真实测试接入必需 CI 检查，并安排告警、仪表盘和权限等部署侧验收。
