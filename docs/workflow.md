# 开发流程

## 1. 定义变更

引用现有规格或复制 `templates/feature-spec.md`。记录目标、非目标、业务规则、异常、权限、交互和验收场景。复杂变更可用 `templates/change-plan.md` 记录计划并随 PR 提交；简单变更无需额外文档。

人提供目标后，AI 可以负责起草规格和任务拆解，但必须把业务实现、日志/指标/trace、验证与排障作为同一交付范围。适用的通用规则见 [可观测性基线](../specs/observability.md)，具体采集设计见 [可观测性设计](../architecture/observability.md)。重大业务取舍和风险接受仍需负责人决定。

每条关键规则使用项目内唯一且稳定的 ID，例如 `REF-001`。删除规则时保留废弃说明，不把旧 ID 分配给不同含义。功能索引引用规格，不复制规则。

## 2. 审阅规格

规格状态：草案 → 待审阅 → 已批准；不再适用时标记已废弃。批准记录应链接到真实 PR/Issue 等证据，不由 AI 自行填写“已批准”。

交付状态单独记录在 `product/capabilities.md`：未开始、进行中、已交付、已下线。规格已批准不代表功能已交付。

关键未决问题解决后才能实现相关逻辑。权限、资金、不可逆删除、数据迁移等高风险变更，先批准规格与回滚或恢复方案。

## 3. 实现与验证

在同一 PR 中更新规格、契约、实现和相关测试。测试名称或注释引用规则 ID。

| 约束 | 推荐验证 |
| --- | --- |
| 业务规则 | 单元测试、属性测试 |
| 接口兼容性 | 契约检查、兼容性测试 |
| 并发、重试、状态一致性 | 集成测试 |
| 关键用户路径 | 端到端验收 |
| 架构依赖 | 静态依赖检查 |
| 性能 | 有指标与环境说明的基准或压测 |
| 可观测性 | 实际导出/查询、上下文关联、脱敏、基数与采样测试、采集故障注入 |
| 易用性、视觉 | 有负责人和记录的人工评审 |

规则与测试关联并不代表覆盖充分。高风险场景还需检查并发、超时、重试与恢复。

## 4. 评审与合并

使用 PR 模板提交实际验证证据。纯文档、重构等无行为变化的改动可说明不更新规格的理由。

完成定义：

- 相关规则明确，必要审批完成；
- 实现符合范围，没有未经批准的行为变化；
- 必需检查通过，人工验收有记录；
- 关键路径具备适用的三类信号；[可观测性验收](../tests/acceptance/observability.md) 有实际结果，告警及 runbook 已验证，裁剪有批准；
- 风险、兼容性、迁移和回滚/恢复方案已说明；
- 功能索引状态真实，未验证部分明确列出。

CI 成功不是人类批准，也不自动代表业务验收完成。GitHub 合并约束由平台规则配置。

## 5. 发布与反馈

按风险配置灰度、监控和回滚。将服务版本与遥测关联，明确告警接收者、无数据检测和恢复验证；观测采集异常不能被误解为业务没有错误。缺陷应回溯相关规则：是规格遗漏、实现偏差还是验证缺口？修复时补齐对应资产，不只修改代码。
